# 讨论、研究与版本管理流程

## 接续顺序

每次新会话、上下文压缩后或更换协作者时，先读 [README](../README.md)、[当前状态](PROJECT_STATE.md)、[决策记录](DECISIONS.md)、[路线](ROADMAP.md)，再读相关主题规格。不要仅凭聊天摘要推断所有参数都已获得批准。

当前优先级是完成文档基线。新数据审计暂停；后续依用户恢复指示推进。用户一直要求先讨论、先不写系统代码。

## 一轮讨论如何落盘

1. 确定这一轮要解决的问题，提出具体建议并解释金融意义、替代方案和限制。
2. 将结论分为已接受、研究默认、假说、证据或未决，写入对应主题文件。
3. 有实质性决定时更新 DECISIONS；改变阶段、阻塞或下一步时更新 PROJECT_STATE 和 ROADMAP。
4. 资料引用写到 REFERENCES；实测记录保留请求、范围、关键数值、检查和未检查项。
5. 检查跨文件数字、术语和链接；到有意义的里程碑创建 Git 提交，并在授权范围内同步远端。

不要求每句话提交一次，但不能把唯一的关键决定长时间只放在聊天里。记录可核查的理由与取舍，不保存无法审阅的内部思维过程，也不把探索过程写成确定结论。

## 数据与实验记录

数据审计区分：文档宣称、公开网页可读、真实接口请求成功、小样本质量通过、完整范围通过。每一步都需要自己的证据，不能跳级。

未来正式数据快照至少记录来源、抓取时间、参数、版本、时区、覆盖期、行数、质量结果和内容校验值。今天有限审计没有保存完整原始响应或其哈希，不能事后伪造。结构化摘要仅保存已经观察到的有限事实。

未来每次实验预先记录问题、假说、股票池、特征、标签、切分、成本、约束、参数范围和验收；运行后追加结果和失败。保留全部试验，测试集使用史也要记录。数据、模型、配置和账本版本必须能对应；不能只提交一张收益图。

## Git 约定

用户已要求在当前 GitHub 项目做版本管理。当前仓库远端为 RightLoop/Spl_Trading，首次文档化前为初始 main 分支。本次使用普通提交保存文档基线，不改写已有历史。

- 修改前看工作区，明确哪些是用户已有文件与本轮文件；只暂存任务相关内容。
- 新建分支默认以 codex/ 开头；小型文档里程碑可在当前分支正常提交。
- 提交信息写具体结果，例如“docs: record investment research baseline and data audit”。
- 提交前检查差异、相对链接、结构化数据和状态一致性。纯文档变更不引入无关应用测试。
- 同步只做普通推送；遇远端新提交先读取差异，不强制覆盖、不擅自丢弃用户改动。
- 远端认证或网络失败时保留本地提交，并明确“已本地提交、未同步”的真实状态。
- 令牌、账户密钥、个人账号资料和批量原始行情不进入文档提交。未来数据目录与忽略规则待数据方案确定。

此环境存在 Git 仓库所有者与运行用户不同的情况。已使用仅对当前命令生效的精确仓库 safe.directory 设置读取仓库，不应为方便全局信任所有目录。具体执行和提交号以 Git 历史与交付消息为准。

## 修订时必须保留的边界

不能把研究默认写成用户已批准，把提供方说明写成实测，把样本可用写成全历史完整，把论文中的效果写成本项目收益，把回撤容忍写成保证上限，把虚拟收益写成小额可执行结果。发现错误时清楚记录纠正原因及受影响结论。
